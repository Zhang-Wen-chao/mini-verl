# Qwen3.5-4B PPO vs standard GRPO：公平开发对照契约

状态：**已完成。** 首次 PPO 5-step 在第 1 次 Critic 反传因显存不足停止；保留该容量边界后，
以不改变样本预算的 Critic activation-offload 重试完成 PPO 5-step，并自动串行完成同契约的
standard GRPO 5-step。两腿均通过稳定性门；尚未启动 20-step 开发对照。

## 为什么不是直接比较旧运行

刚通过的 PPO 1-step 只使用每步 3 条 trajectory；已有 GRPO 开发运行使用每步 3 prompts times
4 rollouts，即 12 条 trajectory。直接比较二者会把 rollout 数不同误写成算法效果。本对照从同一
Qwen3.5-4B base checkpoint 重新开始，固定每步 3 prompts times 4 rollouts，共 12 trajectories。

## 两种公平性，分开报告

PPO 额外训练 4B Critic，故不可能同时让更新数、rollout 数与 GPU-hours 全部相同。项目将回答
两个不同问题：

1. **固定样本预算（当前）**：两边相同的 prompts、rollouts、长度上限、数据顺序、seed 和
   3 trainer + 1 rollout 拓扑。它衡量同样训练信号下的开发变化、稳定性和样本效率，同时如实
   报告 PPO 的额外时间/显存成本。
2. **固定计算预算（后续）**：用当前测得的每-step GPU 时间，缩短较慢算法使总 GPU-hours
   相等。它衡量同样成本下的效率，不能取代固定样本预算的结论。

由于从第二步起两种策略已不同，无法也不应强行让生成 token 完全相同；改为固定完成次数和
token 上限，并记录每腿的实际 total tokens 与 step time。

## 冻结的 5-step / 20-step 契约

| 变量 | PPO | standard GRPO | 说明 |
|---|---:|---:|---|
| Base model / train rows | Qwen3.5-4B / 相同 2037 OpenR1-Math rows | 相同 | 不从旧 checkpoint resume |
| Seed / 数据顺序 | 42 / shuffle=False | 相同 | 固定 actor、data loader、rollout seed |
| 拓扑 | 3 FSDP2 Actor + 1 TP=1 vLLM | 相同 | PPO Critic 为 pinned entrypoint 所要求的 FSDP1 |
| 每步训练信号 | 3 prompts times 4 rollouts = 12 trajectories | 相同 | 两腿最重要的共同预算 |
| 长度上限 | prompt 512 / response 384 / model 896 | 相同 | 既有非退化 reward 的短回答契约 |
| Actor LR / KL / sampling | 1e-6 / 0.001 / temperature 0.8, top-p 0.95 | 相同 | Critic LR=1e-5 仅 PPO 所需 |
| Advantage | GAE, gamma=1, lambda=1 | group relative reward, std normalization=true | 唯一算法性差异；PPO 另有 value Critic |
| 开发评测 | 相同 MATH 64，训练前与最终各一次 | 相同 | 仅开发遥测，不能作为最终算法胜负 |

验收要求：每一步均有训练指标，最终 checkpoint 和 rollout JSONL 必须存在，actor loss/KL
必须有限；PPO 额外要求 value loss、values、advantages 有限。任何 OOM、NCCL、NaN 或 Inf
都使该腿停止，不进入 20-step。

## 首次 PPO 5-step 的边界与重试

首次完整样本契约的 PPO leg 为
`qwen3.5-4b-fair-ppo-5step-seed42-20260822T122730`。它通过 CUDA/runtime/lock
preflight、Ray 启动、初始 64 题监控（41/64 = 64.1%）、第一次 rollout、GAE、Critic 前向和
Actor 更新，但在第一个 Critic backward 的 FSDP1 reduce-scatter 中失败：`F.pad` 申请
2.49 GiB 时仅余 2.34 GiB（该 Critic 进程占 39.35 GiB）。因此没有完整 update、没有
`global_step_5` checkpoint，不能产生 PPO 质量结论，也不会提前运行匹配 GRPO leg。

失败前的有限遥测为 `critic/vf_loss=1.306661`、`critic/values/mean=-0.203408`、
`critic/advantages/mean=2.43e-08`、`actor/loss=0.000582`、`actor/ppo_kl=0.009969`、
`critic/rewards/mean=0.333333`、`perf/total_num_tokens=3382`、`timing_s/step=114.62`。
这排除了在首次 backward 前的数值发散；失败原因是完整 12-trajectory Critic backward 的
显存峰值。artifact 保留在 L20 的持久目录，未删除。

不能把 `critic.ppo_mini_batch_size` 从 3 改成 1 来逃避该峰值：runner 会将它乘以
`rollout.n=4`，得到全局 mini-batch 4，而 3 个 FSDP rank 要求该数能被 3 整除；最小合法值
仍为 12。重试因此保持 3 prompts times 4 rollouts、长度、seed、Actor 配置和 Critic 学习率
不变，只打开 `critic.model.enable_activation_offload=true`，将保存的 Critic activation 转至
CPU。它是资源配置变化，预计更慢；会单独报告其 step time 和显存，不能伪装成算法优势。

已启动的 PPO watcher 另有一个只读监督器
[`continue_fair_grpo_after_ppo.sh`](../../continue_fair_grpo_after_ppo.sh)：它只观察 PPO 的
`FAIR_COMPARISON_LEG_FINISHED` gate。仅在 PPO 连续 5 个有限 update、checkpoint 和 rollout
artifact 均通过后，才启动同一 shared-rollout contract 的 GRPO；PPO 有任何 gate failure 时，它
停止并留下原因，绝不会运行单独的 GRPO 后误称为算法对照。

部署注意：这两个 watcher 必须通过 `nerdctl exec ... zhangwenchao-megatron` 在训练容器内运行。
宿主机能运行 `nvidia-smi`，但其 Python runtime 不能初始化 CUDA；一次宿主机 watcher 因此在
preflight 停止，未创建 Ray、未占用 GPU、未开始 PPO。该 artifact 同样保留为部署诊断，不计入
算法实验。

共享节点还出现过一次首次空闲检查后、CUDA/Ray preflight 期间有外部作业重新领取四卡的竞态。
该 PPO/Ray 进程组在首个训练 update 前被终止，外部 PID 未触碰；它不产生任何实验结论。runner
CUDA/runtime preflight 现被前置到 idle wait 之前（它不构建模型也不预留 GPU）；在四卡空闲后
runner 只做一次即时二次检查便创建 Ray/vLLM。若这个极短窗口内仍变忙，会回到 idle wait 并继续
等待，直到 12 小时窗口结束，而不是在混合占用下运行或需要人工重启。

## 已完成的 5-step 固定样本预算对照

两腿均从 Qwen3.5-4B base 重新开始，使用冻结契约中的相同 2,037 条训练数据、seed=42、
`shuffle=False`、3 trainer + 1 vLLM rollout 拓扑、每步 3 prompts × 4 rollouts = 12 条
trajectory、相同长度上限及 Actor LR/KL/sampling。PPO clean retry 的 artifact 是
`qwen3.5-4b-fair-ppo-5step-seed42-activation-offload-clean-20260822T130000`；匹配 GRPO
artifact 是 `qwen3.5-4b-fair-grpo-5step-seed42-clean-20260822T130000`。二者都保存了
`rollout_samples/1..5.jsonl`、最终 `validation_samples/5.jsonl`、`global_step_5`，并且
watcher exit code 均为 0。

| 指标 | PPO / GAE + 4B Critic | standard GRPO | 应如何理解 |
|---|---:|---:|---|
| 完整 update / 样本预算 | 5 / 5 × 12 = 60 trajectories | 5 / 5 × 12 = 60 trajectories | 本次比较固定的是 rollout 样本数，不是 GPU-hours。 |
| 64 题开发 monitor | 41/64 (64.1%) → 45/64 (70.3%)，+4/64 | 40/64 (62.5%) → 42/64 (65.6%)，+2/64 | 两腿初始值不同，且这 64 题被反复读取；不能据此宣称 PPO 或 GRPO 更好。 |
| 训练 loop wall time | 8m35s | 6m42s | 包含 5 次 update、最终开发验证和 checkpoint；不是严格的纯训练计时。 |
| 第 5 步时间 / token | 85.62s / 4,039 | 68.65s / 3,603 | 生成长度会随已分叉的策略不同；记录实际值，不把 token 差异伪装成算法效果。 |
| Actor 最大 allocated GPU memory | 35.70 GB | 31.53 GB | PPO 还同时训练 Critic；该数字是本轮每侧记录到的 Actor 指标峰值。 |
| 最后一步 KL | 0.01027 | 0.01158 | 两边均为有限值，且使用相同 reference KL coefficient 0.001。 |
| 数值 / 系统健康 | Critic value loss、values、advantages、Actor loss/KL 均有限；无 OOM/NCCL | Actor loss/KL/advantage 均有限；无 OOM/NCCL | 两腿均通过 gate，不是仅凭进程退出码判断成功。 |

PPO 采用 `critic.model.enable_activation_offload=true`，这是保持完整 12-trajectory batch 后
避开首次 Critic backward OOM 的唯一资源实现改动；它把 Critic 保存的 activation 转到 CPU，
不改变 PPO 目标、reward、rollout 数或训练数据，但增加了 CPU 内存/数据传输成本。因此本轮最强的
结论是：在该 4×L20 配置和完整样本契约下，**真实 4B actor--critic PPO 可稳定完成**；相对
GRPO，它在这一次短运行中消耗了更多 wall time 和 GPU memory。它不构成质量或样本效率的胜负结论。

首次未开启 activation offload 的 PPO OOM artifact、宿主机 CUDA preflight artifact 和外部 GPU
竞态 artifact 全部保留；它们是容量/部署证据，不计入上表的算法遥测。

## 解释边界

5-step 只确认放大到四个 rollout 后两侧都稳定，并量到 PPO 的资源代价；20-step 的 64 题变化
也只能用于 development telemetry。已有 MATH held-out 200 已被过去 679-step GRPO 读取，
不能在本短开发对照中反复读取后再称为全新 final。若推进算法质量比较，应先固定新的
development/final split、停止规则和至少多个 seed；随后在固定样本预算与固定 GPU-hours 两种口径下
分别报告 PPO/GRPO。

运行器 [await_fair_algorithm_comparison.sh](../../await_fair_algorithm_comparison.sh) 只会在四张
GPU 均空闲时启动，不会终止或修改外部进程。
