# Qwen3.5-4B no-std calibration: runtime compatibility block

## Outcome

The bounded 20-step no-std GRPO calibration was **not run**.  It stopped before
model construction, rollout, a GPU update, checkpointing, or a quality
measurement because the restored Python runtime cannot initialize CUDA on the
current L20 host.  This is an environment compatibility finding, not evidence
about GRPO, reward normalization, or the no-std ablation.

## Scope and artifacts

| Stage | Artifact root | Result |
| --- | --- | --- |
| 20-step no-std calibration | `qwen3.5-4b-openr1-grpo-nostd-20step-trainer3-rollout1-20260822T0157` | stopped at NCCL initialization |
| 170-step no-std development run | `qwen3.5-4b-openr1-grpo-nostd-170step-trainer3-rollout1-20260822T0202` | correctly refused: calibration failed |
| 170-step standard-GRPO control | `qwen3.5-4b-openr1-grpo-standard-170step-trainer3-rollout1-20260822T0216` | correctly refused: no-std gate failed |

All three artifact roots are retained under:

```text
/mnt/storage01/zhangwenchao02/repos/mini-verl-l20/artifacts/
```

The second and third gates terminated normally after reading their predecessor's
`logs/gate_failure`; no queued long run was launched.  At inspection time the
four L20s had no compute process.

## Evidence

The host reports four NVIDIA L20s, driver `550.127.05`, and CUDA driver API
version `12.4`.  The rebuilt disposable runtime at
`/tmp/official-verl-local-fsdp-vllm` contains the current pinned stack:

```text
torch 2.11.0+cu130
vLLM 0.24.0 (requires torch == 2.11.0)
verl 0.10.0.dev0
Python 3.12.12
```

During Ray worker startup, PyTorch reports:

```text
CUDA initialization: The NVIDIA driver on your system is too old
(found version 12040)
ValueError: ProcessGroupNCCL is only supported with GPUs, no GPUs found!
```

Thus the CUDA 13.0 PyTorch wheel was accepted by the bootstrap's import check
but rejected when it initialized the host driver.  The initial launcher wrote
`logs/exit_status = 1` and the calibration watch gate wrote
`calibration launcher exited with status 1`.  It produced no rollout JSONL,
checkpoint, or learning metric.

## Guardrail added

`official_verl/preflight.py --require-cuda` now requires both `nvidia-smi`
visibility and a subprocess probe of the *selected* interpreter's
`torch.cuda.is_available()` and device count.  This makes the driver/runtime
mismatch fail before Ray workers or NCCL initialize.  A focused unit test covers
the case where `nvidia-smi` sees an L20 but PyTorch reports zero usable devices.

## Recovery: use the supported experiment container

No GPU-driver update was attempted. Updating a shared NVIDIA driver is an
infrastructure change and needs separate explicit approval. The persistent
CUDA-13 locked runtime and the completed 679-step artifact are unchanged.

The failure is specific to launching the disposable venv directly on the L20
host. The same exact interpreter and package set, run through the existing
`zhangwenchao-megatron` experiment container, reports:

```text
torch 2.11.0+cu130
torch.cuda.is_available() == True
torch.cuda.device_count() == 4
```

The container also passes the updated locked preflight, including its real CUDA
probe. Its base NVIDIA PyTorch (`2.10.0a0+nv26.01`, CUDA 13.1) independently
sees the same four GPUs. This shows that the original source lock is usable
without altering its packages; the supported execution context supplies the
required CUDA runtime view.

All follow-on calibration gates therefore run **inside that experiment
container**, while reading the same shared `/mnt/storage01` repository and
writing fresh timestamped artifacts there. Direct host launches remain blocked
by the strengthened preflight.
