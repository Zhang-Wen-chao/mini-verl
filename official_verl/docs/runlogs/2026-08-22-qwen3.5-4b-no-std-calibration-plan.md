# Qwen3.5-4B no-std GRPO 20-step calibration plan

## Question

With Qwen3.5-4B, the locked 2,037 OpenR1-Math rows and four rollouts per prompt,
does removing GRPO's group-standard-deviation division start and train stably on
the validated 3 FSDP2 actor + 1 TP=1 vLLM topology?

This is a feasibility and signal-scale gate, not a quality claim or a PPO
comparison.

## Frozen contract

- Base model: `Qwen3.5-4B`; do not resume a prior calibration checkpoint.
- Train input: `training-2037-processor-filtered-openr1-math-v5-short-20260819T1919.parquet`,
  SHA-256 `acc92db0d549dc9d9996162f620df6db2d871ecf16af971a0b14fd9b84ced567`.
- Validation input: `calibration-math-test-64-v3-short.parquet`, SHA-256
  `b3208ca66648232a2ef77b479c5a4b34bd242b7e99c170e715db0f83cf7527d7`.
- 3 actor GPUs, 1 rollout GPU, TP=1; train batch 3, rollout `n=4`, 12 agent
  workers; prompt/response/model limits 512/384/896.
- Legacy pinned `math_reward`, temperature 0.8, top-p 0.95, actor LR `1e-6`,
  KL coefficient `0.001`, all unchanged from the formal run.
- Total steps 20; checkpoints and frozen 64-row validation at step 20.

## Sole changed variable

```text
algorithm.norm_adv_by_std_in_grpo=false
```

The upstream default is `true`. With binary rewards and group size four, this
removes a reward-composition-dependent scaling factor; it does not add a critic,
change PPO clipping, change the reference KL, or change which reward groups are
degenerate. See [the offline audit](../../../docs/results/grpo-advantage-standardization-audit.md).

## Launch gate and acceptance criteria

Before launch: restored pinned Python runtime imports `torch`, `transformers`,
`ray`, `vllm`, and `verl`; preflight sees the locked source and four CUDA GPUs;
no foreign compute process is present.

Accept only if `exit_status=0`, `global_step_20` is complete, checkpoints and
rollout samples exist, no OOM occurs, mixed reward groups yield non-zero actor
gradients, KL remains finite, and response-cap behavior is not catastrophically
worse than the prior contract. A 64-row monitor movement is health telemetry only
and is not evidence that no-std GRPO is better.

If the gate fails, record the first concrete failure and stop rather than
escalating to 170 steps. If it passes, commit the run record before any longer
development run.
