# mini-verl 踩坑记录

实验：Qwen3.5-4B GRPO，2037 题训练 679 步，4×L20，已跑完。
本章记录评测/验收阶段踩到的坑与落地经验，供后续实验复用。

- 坑 1–5（2026-08-20）：数学 GRPO 那轮的评测/验收坑。
- **坑 6–10（2026-09-28）：SWE / agentic RL 那轮补的，但都是与任务无关的工程判据。**
  它们的共同点是 —— **不报错、日志干净、结论看起来完全正当**，症状是一个恒为 0 的计数
  或一个「看起来更合理」的孪生口径，而不是异常。取证见
  [SWE-GRPO on 2×L20](../results/swe-grpo-l20-negative-result.md) 的「四处静默失效」。

## 坑 1：评测脚本 greedy 解码卡死（本次实际遇到）

### 现象
- 自写 held-out 评测脚本（HF `generate` + greedy + `max_new_tokens=768`）跑 base 模型，
  日志停在某个 step 后 10 分钟无推进。
- 进程状态：GPU 利用率降到 ~54%，CPU 133%，显存占用不变 —— 典型的"在算但不出结果"。
- 根因：**某道难题让 greedy 解码陷入重复循环**——模型反复生成几乎相同的 token 序列，
  `<eos>` 永不出现，直到撞上 768 token 上限；单题无超时，整个 200 题评测全废。

### 为什么会这样
- greedy 解码在长序列 + 难题上容易陷入局部循环（模型在同一个"念头"上打转）。
- 训练时的 rollout 用 vLLM + sampling，vLLM 有 `max_num_batched_tokens`、chunked prefill
  和截断保护，采样天然不易死循环，所以训练没踩到。
- 评测脚本图省事用了最朴素的 HF generate，**没有任何超时/重复检测**。

### 修复
1. 单题生成加 120s 硬超时（`signal.alarm`），超时整题判错跳过。
2. 评测**逐题落盘**（每完成一题立即 append + flush），不再"跑完才写"——卡住/崩溃不丢进度。
3. 单题 try/except 包裹，一道题炸了不中断整个评测。

### 经验
- **任何长序列解码都要有超时**：`signal.alarm` 或重复 n-gram 检测，二选一必须。
- **评测脚本必须逐题落盘**，跑完才写 = 一崩全丢。
- 生产评测建议用 vLLM 而非裸 HF generate（有截断/批处理保护），或至少加 `repetition_penalty`。
- 卡死诊断口诀：日志 10 分钟不动 + GPU 低利用 + CPU 高 = 解码循环；日志不动 + GPU 满 = 在算（正常）。

## 坑 2：答案评分器对"等价数字格式"不鲁棒（误杀）

### 现象
训练中 64 题评测，step 510→679 表面 56→53（掉 3 题）。逐题人工判定后发现：
- 6 道"回落"题里 **2 道是评分器误杀**：
  - 模型答 `\boxed{5.5}`，标准答案 `\frac{11}{2}` → 5.5 ≡ 11/2，数学等价却被判错
  - 模型答 `\boxed{3.5}`，标准答案 `\frac{7}{2}` → 同理误杀
- 修正后实际约 55/64 = 85.9%，非表面 82.8%。

### 根因
训练用的 rule reward / eval 评分是**精确字符串比较**，不归一化分数↔小数、不化简、不处理符号等价。
训练后期模型倾向把分数写成小数（5.5、3.5），撞上精确匹配直接判错。

### 修复（held-out 评测脚本已实现）
归一化比较：
1. 解析 `\boxed{...}` 用**花括号配对**（处理 `\boxed{\dfrac{9}{7}}` 嵌套），非简单正则。
2. 答案归一化：`\frac{a}{b}` → Fraction 精确值；小数 → `limit_denominator` 转分数再比；
   空格/逗号/反斜杠剥离。
3. gt 从 solution 的最后一个 `\boxed{}` 提取（MATH-lighteval 格式）。

### 经验
- **RL 的 reward 必须做答案归一化**，否则模型会"学会用格式逃逸"——不是学数学，是学怎么让字符串匹配。
- 训练中 eval 的准确率**只能信到"格式不变时"的相对变化**；跨格式结论要人工抽查。
- 教训：监控 64 题"回升/回落"之前，先确认评分器不会因格式漂移误判。

## 坑 3：MATH-lighteval 的 solution 答案格式

- MATH-lighteval 的 ground truth 藏在 `solution` 字段，结尾是 `\boxed{...}`（
  `\boxed{2}`、`\boxed{\dfrac{9}{7}}`），不是独立 answer 字段。
- 简单正则 `\\boxed\{([^}]*)\}` 对嵌套花括号（`\dfrac{9}{7}`）会截断成残缺串。
- 必须用花括号配对解析（见坑 2 修复）。

## 坑 4：容器/宿主路径与 venv 混淆

### 现象
- 宿主机 `ps` 看到训练进程路径 `/tmp/official-verl-local-fsdp-vllm/venv/bin/python`，
  但宿主机 `/tmp` 下**没有**该目录 → 训练实际跑在容器里，进程名映射出来的路径是"假象"。
- 在宿主机直接调 venv python 报 `No such file or directory`。

### 修复
- 一律通过 `nerdctl exec -w / <container> <cmd>` 进容器执行。
- 判断训练在哪个容器：`nerdctl ps` + 容器内 `ps aux` 交叉确认。

### 经验
- 看到宿主机上的容器路径不要直接 cd/exec，先进容器。
- 判断"进程是否在容器"：`readlink /proc/<pid>/exe` 若指向容器内路径则说明在容器。

## 坑 5：vLLM 显存瞬时读数误导（GPU 利用率 0% 不代表卡住）

### 现象
- 训练中途 `nvidia-smi` 抓到 GPU 0-2 util 0%、GPU 3 42%，以为卡住。
- 实际是 rollout 与训练切换瞬间的采样空隙，30 秒后恢复 100%。

### 经验
- 判断训练是否卡死：**看日志/tfevents mtime 是否持续更新 + 进程是否存活**，别只看单次 nvidia-smi 快照。
- GPU util 单点读数不可靠，至少要隔 30s 取两次。

## 坑 6：配置开关是逐跳白名单，传不到也不报错

### 现象
整轮评测（6 个点 × 5 片）全部跑在**冒烟档 15 步**上，而日志、启动参数 dump、产物
全都正常。这轮的留出池读数 `5.8% → 6.0%，p = 1.0000` 看起来是「确认无迁移」，
实际正确的读法是**「读不出」** —— 15 步把基座和训练点**截断在同一个地方**，
一个需要 25 步才做完的题两边都失败 ⇒ 效应被压向 0。

### 根因（两跳，都静默）
1. launcher 里写的是 `export SWE_AGENT_STEP_LIMIT="${SWE_AGENT_STEP_LIMIT:-15}"`。
   `${VAR:-default}` 的语义是「**未设置时**才用默认值」—— 它把「冒烟用的小值」
   固化成了生产默认；而代码里的默认值是 40。
2. 发现后想「只在外部 `export` 成 40、不动脚本」，实测三行就被否掉：

   ```bash
   export SWE_AGENT_STEP_LIMIT=40
   echo "[$SWE_AGENT_STEP_LIMIT]"                              # → [40]  ✅
   sudo nerdctl exec <容器> bash -c 'echo [${SWE_AGENT_STEP_LIMIT:-未设置}]'
                                                               # → [未设置] ❌
   sudo nerdctl exec -e SWE_AGENT_STEP_LIMIT=40 …               # → [40]  ✅
   ```

   **`nerdctl exec` 的容器内环境来自容器，不来自客户端；只有 `-e` 能穿这一跳。**
   如果没先测，整轮重测会**静默跑成第二个 15 步**，并据此写下「40 步也没用」。

### 经验
- 配置是**逐跳白名单**：设了 ≠ 传到了 ≠ 生效了。**「环境变量名」和「它的值」
  要分别取证，而且要在运行时现场取。**
- 查 mtime、查脚本内容只能证明「写过」，不能证明「跑的时候是这个值」。
  **唯一有分辨力的证据是产物里的那个值** —— 读正在运行的 job 的 `env_vars`。
- **修好传递链之后，必须做阳性对照才允许发车**：起飞后读运行中 job 的 `env_vars`，
  要逐字出现目标值。本次阳性对照通过，逐字出现 `"SWE_AGENT_STEP_LIMIT": "40"`。
- 把这类值做成**发车前置断言**，不靠事后审计。落地脚本见
  [analysis/preflight_steplimit.sh](../results/swe-grpo-l20-analysis/preflight_steplimit.sh)
  （`< 40` 且未显式声明冒烟 ⇒ `exit 1`）。

## 坑 7：按名字匹配的判据，换命名后静默失效（症状是计数恒为 0）

### 现象（同一类，连中三处）
1. 磁盘清道夫与端口守卫的自退判据是 `pgrep -f 'run_eval_ladder[0-9]*\.sh'`。
   `run_eval_ladder5.sh` 匹得上；新一轮叫 `run_eval_ladder6_step40.sh` 就**匹不上**
   （`[0-9]*` 吃掉 `6` 之后要跟 `.sh`，实际跟的是 `_step40.sh`）⇒ 两个守护**立刻自退**，
   不报错：阶梯照跑、日志干净，只是磁盘没人收、端口没人看。
2. 清道夫按名字前缀筛目录，前缀写死 `eval_r2_`；新一轮产物叫 `eval_r2s40_*`
   ⇒ **那些目录连被检查都没被检查过**，每次都报「共清理 0 个」。后果不是「清理变慢」，
   而是磁盘从 321G 掉到 254G，逼近阶梯自己 `MIN_FREE_G=250` 的发车断言 ——
   **一个「看起来正常」的 0，掩盖了一个正在逼近的硬停。**
3. 清道夫的「已判完整」表键是 `(分片, 点)`，**不带 tag** ⇒ 上一轮的结论会落到这一轮的
   目录上。这一处**至今没修**；改的是**判断次序**（无条件先过「10 分钟内无写入」这道闸
   再查表），于是键错了只影响「为什么删」这行说明文字，不再影响删不删。

### 经验
- **症状是计数恒为 0，不是报错。** 凡是「按名字过滤/按名字匹配」的判据，换命名之后
  要看的不是「有没有报错」，而是**它这一轮到底动过几个东西**。
- `eval_r2_` 与 `eval_r2s40_` 这种「前缀是另一个前缀的前缀」最阴。
- 注释里写的「匹配任意版本」「换版本时不用重启」是**作者的意图，不是代码的行为**，
  要当待验证的断言读。
- 任何「已处理过什么」的表，键要带**完整标识**（含 tag / 轮次），否则跨轮碰撞。
- 同一条坑连「谁在看着你」那一层都骗过了：值守脚本自己的计数也用了同一个 pattern。

## 坑 8：守卫量的挂载点 ≠ 资源实际落的挂载点

### 现象
评测阶梯有个守卫 `free_g()`（阈值 250G）防止拉镜像塞满共享盘。
它 `df` 的是**数据盘**，而镜像实际落在**另一块盘**上：

| 盘 | 余量 | 被守吗 |
|---|---:|---|
| 数据盘 | 438 G | ✅ 被守（一直没触发） |
| 镜像盘 | **130 G** | ❌ **完全没被守** |

后果：要加 ~180 道非 django 题需要 180 × 2.05 GiB ≈ 369 GiB，而镜像盘只有 130 G，
**缺 239 GiB** —— 但这个缺口**永远不会有守卫报警**。

### 经验
- 凡是「守卫阈值」，先问**它量的挂载点和这个资源实际落的挂载点是不是同一个**。
- 这是同一项目里**第二次**犯「守卫的量纲和资源的量纲不一致」这一类错，所以它值得
  做成一条检查项，而不是一次事故复盘。

## 坑 9：分析脚本自己算出来的东西，不能自己给自己当判据

### 现象
用训练产出的 200 个 rollout dump 重算训练池曲线时，发现 dump 的 `samples` 列表里
**字面重复**（同一 `(rollout, 题, index)` 出现多次，奖励 0 处不一致）。两条内部证据
都指向「去重才对」：① 去重符合直觉；② 去重后每 20 步桶的样本数**恰好** 640 = 20×4×8，
与声明的协议**逐字吻合**。差一点就把「文档曲线用了未去重计数，应更正」写进文档。

### 击穿它的是什么
**训练器自己日志里的 `rollout/raw_reward`**（每批的样本级平均 reward）—— 一个
**被分析系统之外、但同源**的数。逐 rollout 对照：

| 口径 | 与训练器的差 |
|---|---|
| 原样（不去重） | 60/61 逐点一致，平均差 **0.00%** |
| 去重 | 系统性偏高 **+3.5pp** |

⇒ 那些「重复」**就是训练器真正吃进去的批次**。去重会把整条曲线整体抬高约 3.5pp，
**而曲线形状照样单调、照样好看** —— 没有任何内部信号提示它错了。

### 经验
- **分析脚本自算的比率/曲线，不能自证。** 去找一个**被分析系统之外**、但同源的数
  （训练器/服务端/上游自己报的指标），**逐点**对照 —— 不要只比桶均值，
  **均值会互相抵消出假吻合**。
- 分母要问的是「**系统实际吃进去的是什么**」，不是「我认为应该是什么」。
- **「看起来更干净 / 更符合直觉」不是证据**，反而是最容易被它骗的时刻。
- 逐点对照还会暴露汇总看不出的离群；离群**先查自己的数据提取谱系**（实例：那 61 个数
  来自三段不同的 run —— attempt1 覆盖 0–9、attempt2 只有 10、主日志 50–99 ——
  是提取混淆，不是数据缺陷）。
- 可重跑的实现见
  [analysis/roll_compare.py](../results/swe-grpo-l20-analysis/roll_compare.py)。

## 坑 10：修正一个判据之后，要回头检查被它连带放宽的每一处判据

### 现象
「配对设计必须用配对检验」这条修正本身是对的（见坑 1 之前的 2σ 误用）。但在这个修正
被确认之后，又得到一个很强的结论：**86 题上变好 17 / 变差 0，McNemar p < 0.001**。
**这条结论不成立，已撤回。** 因为 `86 = 66 道新题 + 20 道留出题`，而其中 **21 道是训练过的题**。
把判别对按污染与否拆开：

| 子集 | 题数 | 变好 | 变差 |
|---|---:|---:|---:|
| 训练池里的题 | 21 | **14** | 0 |
| 干净的题 | 45 | **1** | 0 |

⇒ 「变好 17」里 **14 个来自那 21 道训练题（记忆）**，干净题上只有 1 个。

### 经验
- **修正一个错误之后，要重新检查被这个修正连带放宽的每一处判据。**
  修正本身对，不等于被它放大的那个结论对。
- 「读不出」有两种相反的病因：**样本量不够**（处方：加数据）vs **检验选错**
  （处方：改算式）。用错公式会让人去加数据，而数据在原设计下根本不是瓶颈。
  下结论前先问「我的检验和我的设计是同一个吗」。
- 一旦某个池子的题被用于调参/选模型，它就不能再用于最终结论 —— 要么留出，要么
  在做检验时把污染子集拆出来单算。

## 经验汇总（速查）

| 场景 | 必须做的 |
|---|---|
| 长序列解码（评测/生成） | 单题超时 + 逐题落盘 |
| RL reward / 评测评分 | 答案归一化（分数/小数/符号） |
| 提取 `\boxed{}` | 花括号配对，处理嵌套 |
| 远程容器进程 | 先进容器再操作，别信宿主机路径 |
| 判断训练死活 | 看日志/tfevents mtime，不看单次 GPU 快照 |
| 环境变量/配置开关 | 逐跳取证（`nerdctl exec` 只有 `-e` 能穿）；起飞后读运行中 job 的 `env_vars` 做阳性对照；关键值做成发车前置断言 |
| 按名字匹配的脚本/清理器 | 换命名后重测它到底匹不匹得上；看「这一轮动过几个」而不是「有没有报错」；已处理表键要带完整标识 |
| 任何磁盘/资源守卫 | 先确认它量的挂载点 = 资源实际落的挂载点 |
| 自己写脚本算出来的比率/曲线 | 拿被分析系统之外的同源指标**逐点**对照；「去重/过滤后更干净」不是证据 |
| 用配对设计做检验 | 用配对检验（McNemar/判别对）；且检查池子里有没有被训练污染的题 |
| 修正了一处判据 | 回头检查被它连带放宽的每一处判据 |
